## Rollback guidance

There is no "unpublish" that preserves trust, and this project's releases are
immutable by policy: a published tag is never moved and a published asset is
never overwritten. Rollback therefore means **redirecting users forward or
backward to a different immutable release**, never editing this one.

If a defect is found in `v0.5.2`:

1. **Do not delete or edit the `v0.5.2` tag, release, or assets.** Anyone who
   already downloaded them holds bytes that must stay verifiable against the
   published checksums.
2. **Re-point "latest" to the last good release** if the defect is severe
   enough to warrant it. `v0.5.1` is intact at
   `49e2cbbc7590af52e648b615c6245ce3cbcee0e9` and can be marked latest again
   (`gh release edit v0.5.1 --latest`). This changes only which release GitHub
   advertises; it neither modifies nor withdraws `v0.5.2`.
3. **Fix forward on the v0.5 line.** Land the fix on `main`, bump to `0.5.3`,
   update `release-state.json`, and publish through the same gated workflow.
   That is the supported path, because the security policy states that fixes
   arrive by publishing a new release rather than by amending an old one.
4. **Record the defect** in a new post-publication record for the release that
   fixes it. This document stays as written.

Downgrading an installation needs no special tooling: install the older archive
into the same prefix. The installer is preview-first, the store format is
unchanged between `v0.5.1` and `v0.5.2`, and **no migration ran**, so moving
between the two in either direction touches no persisted data.
