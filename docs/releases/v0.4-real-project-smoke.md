# v0.4 real-project local smoke (sanitized)

An owner-controlled local smoke of the **installed** `0.4.0` artifact against a
real project, run after the synthetic installed qualification passed
(428/428 checks from each archive).

Only sanitized pass/fail findings are recorded here. **No project content, no
project name, no local path, no snapshot, and no evidence is committed**, and no
log containing private content was uploaded.

## Method

- Built and installed the portable `0.4.0` artifact into an isolated temporary
  prefix; verified the installed CLI and Kernel both report `0.4.0`.
- Captured a real project's Markdown documents three times, editing genuine
  delivery content between captures so real change events were produced.
- Ran the timeline surface from the installed CLI and from the installed stdio
  MCP server against an isolated application-data root.
- Recorded project bytes before and after and compared them.

## Pre-existing defect observed (out of v0.4 scope)

One real-project document could not be **captured**, on both the prepared
`0.4.0` build and the published `v0.3.1` build, with the identical controlled
failure:

```text
memory capture --apply  ->  OMP-R-PB-6006 (snapshot commit failed)
underlying store error:      OMP-MEM-1001 "duplicate evidenceId in commit"
```

The capture pipeline can derive the same evidence id twice for one document when
two distinct derived items minimize to the same evidence fingerprint; the store
correctly rejects the bundle rather than committing a duplicate.

Assessment:

- It reproduces identically on the **published `v0.3.1`** build, so it is a
  **pre-existing v0.3 capture defect**, not introduced by v0.4.
- It is entirely outside the v0.4 scope: Project Timeline only **reads**
  already-committed snapshots and adds no capture path.
- It fails **closed** — the capture is refused, nothing partial is committed, and
  the store stays valid. Every subsequent read, including the timeline, works.
- It does not affect any v0.4 release-truthfulness claim.

It is therefore recorded as a **separate future issue against the v0.3 capture
path**, not a v0.4 release blocker. The remainder of the real project captured
and produced a correct timeline.

## Decision

**GO.** No Blocker, High, or Medium defect attributable to v0.4.
