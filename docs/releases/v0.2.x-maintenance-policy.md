# OH MY PM — v0.2.x Maintenance Policy

## Purpose

This policy defines how the `v0.2.x` line is maintained after the `v0.2.0`
stable release was closed (see
[the post-stable closure report](v0.2.0-post-stable-closure.md)). It scopes what
a patch may change, how a defect becomes a release, and what stays out of scope
until a separately approved development line begins. It starts no feature work
and prepares no patch release.

## Supported Stable Version

- **current stable:** `v0.2.0` — the latest stable GitHub Release.
- **maintenance line:** `v0.2.x`.
- `main` remains at source version `0.2.0` until a separately approved
  maintenance change (a `v0.2.1` preparation) explicitly begins. No `v0.2.1` is
  prepared by this policy.

## Maintenance Scope

A `v0.2.x` patch may contain only:

- bug fixes that preserve the public contract;
- security hardening that preserves the public contract;
- packaging / install fixes;
- cross-platform compatibility fixes;
- corrections to incorrect deterministic extraction, backed by fixtures;
- provider correctness fixes that preserve read-only and bounded behavior;
- documentation corrections;
- release / CI reliability fixes.

## Out of Scope

The following require a **separate, explicit approval** and are not part of
`v0.2.x` maintenance:

- new providers;
- new MCP tools;
- tool renames or ordering changes;
- write-back of any kind;
- HTTP MCP transport;
- telemetry;
- a dashboard;
- provider aliases / profiles;
- new source modes;
- new product features;
- v0.3 architecture;
- self-update;
- automatic MCP client configuration;
- a CLI `--help` surface (deferred follow-up L1).

## Defect Severity

- **Blocker** — the release is unusable for a core journey, produces incorrect
  security/privacy behavior, or breaks installation on a supported platform.
- **High** — a core journey is significantly degraded or produces wrong output,
  but a workaround exists.
- **Medium** — a real defect affecting a non-core path or a core path only under
  narrow conditions.
- **Low** — cosmetic, documentation, or a minor non-blocking gap (e.g. L1, L2).
- **Security** — any issue touching the read-only / bounded / no-secret-leak
  boundaries, handled through private triage first.

## Patch Release Trigger

- **Blocker** → immediate patch preparation.
- **High** → patch preparation after a confirmed reproduction.
- **Medium affecting a core user journey** → patch candidate after triage.
- **Low** → normally documentation or backlog; does not alone trigger a release.
- **Security issue** → private triage first; public disclosure only after
  remediation.

## Patch Development Flow

Every patch follows the quality flywheel, in order:

1. a real, confirmed defect;
2. a minimal reproduction;
3. a sanitized fixture (no secrets, no private paths, no real tokens);
4. a regression test that fails before the fix and passes after;
5. the smallest fix that resolves the defect and preserves the public contract;
6. full validation (build, tests, validate, MCP smoke, version consistency,
   public surface, boundaries, structure);
7. portable-artifact rehearsal (bundle, deterministic archives, installer
   preview/apply/source-removal/relocation, installed ten-tool MCP);
8. explicit release approval;
9. post-publication verification from the public assets.

## Regression Evidence

A patch is not accepted without:

- a regression test committed alongside the fix;
- the sanitized fixture the test consumes (where extraction/provider behavior is
  involved);
- evidence that the test fails on the pre-fix code and passes on the post-fix
  code.

## Release Candidate Decision

- An **RC is required** when a patch changes Kernel behavior, provider behavior,
  MCP schemas, installer/archive behavior, cross-platform packaging, or security
  boundaries.
- A **direct stable patch** may be considered only for low-risk documentation or
  release-metadata corrections, and only with explicit owner approval.

## Patch Release Governance

- Patch releases publish only through the manually gated release workflow with
  `workflow_dispatch`, an explicit version input, and the exact confirmation
  string.
- The publish job runs in the protected `github-release` environment behind the
  required reviewer; no administrator bypass.
- No registry publication (npm, crates.io, or otherwise) at any point.
- Historical releases (`v0.1.0`, `v0.2.0-rc.1`, `v0.2.0`) and their tags and
  assets are immutable and are never modified, deleted, or re-pointed.
- A published release is not silently overwritten; a defect found after
  publication is fixed forward with a new patch, never by mutating a published
  release.

### Operational runbook note

When approving a protected-environment deployment through the GitHub REST API,
the pending-deployments approval endpoint requires `environment_ids` as a **JSON
integer array** supplied through `--input`. A form-encoded `environment_ids[]`
parameter may silently perform no approval.

## Security and Privacy Invariants

Every patch must preserve:

- local Markdown workflows fully offline, reading no token;
- GitHub access explicit, read-only, `GET`-only, single fixed origin, fixed API
  version, single page, optional environment-only token that is never printed or
  persisted;
- no raw comment/review/review-comment bodies, diff hunks, or commit identifiers
  in MCP projections;
- installer writes confined to the explicit prefix, with no PATH, shell-profile,
  project, or MCP-client-config edits;
- no telemetry, no project-file writes, no context upload;
- all packages private; no registry publication.

## Compatibility Rules

- The MCP surface stays at **exactly ten** read-only tools in the fixed order; a
  patch never adds, removes, renames, or reorders tools.
- The CLI command surface, exit codes, and flag semantics are preserved.
- Archive layout (single top-level `oh-my-pm-v<version>/` directory, three
  assets) and the preview-first installer contract are preserved.
- Node.js 20+ remains the only runtime requirement for installed archives.

## Documentation-Only Changes

Documentation corrections that touch no product behavior, no version, and no
release assets may proceed as a docs/process commit without preparing a release,
subject to the same validation gates that apply to documentation
(version-consistency, public-surface, structure, boundaries, build, tests,
validate, MCP smoke all remain green).

## Support Window

`v0.2.x` is the actively maintained line while `v0.2.0` is the current stable.
When a later stable line is separately approved and opened, this policy is
superseded by that line's maintenance policy; until then, `v0.2.x` is the only
maintained line and `v0.1.0` remains a preserved historical stable.

## Escalation and Stop Conditions

- Any change that would fall under **Out of Scope** stops immediately and
  requires separate, explicit approval before proceeding.
- Any change to product behavior, version, Kernel/runtime versions, release
  workflows, installer/archive logic, tags, or releases stops immediately unless
  it is the explicitly approved subject of a maintenance change.
- A suspected security issue stops public work and moves to private triage; the
  fix is remediated before any public disclosure.
- No `v0.2.1` or v0.3 work begins without a separate, explicit instruction.
