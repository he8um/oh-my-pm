# OH MY PM v0.5.0

Stable release opening the v0.5 line. It changes **one** thing — the name you type
— and changes nothing else.

The canonical CLI command family is now `ohmypm`, `ohmypm-mcp`, and
`ohmypm-install`. The former `oh-my-pm` family remains available as deprecated
compatibility aliases, with **no removal scheduled**.

```bash
ohmypm status
ohmypm brief .
ohmypm memory timeline --project-id example
ohmypm mcp-config
```

## This is not a product rename

v0.5 is a CLI command namespace migration. The product, the repository, the
packages, the environment variables, the installation paths, the data
directories, and the release archives are all unchanged.

| Identity | Value |
| --- | --- |
| Product display name | OH MY PM |
| Repository | `he8um/oh-my-pm` |
| Package scope | `@oh-my-pm/*` |
| MCP server registration key | `oh-my-pm` |
| Environment variables | `OH_MY_PM_*` |
| Rust / module identifiers | `oh_my_pm_*` |
| Installation directory | `<prefix>/lib/oh-my-pm/versions/0.5.0/` |
| Release archives | `oh-my-pm-v0.5.0.tar.gz`, `oh-my-pm-v0.5.0.zip` |
| Project config filename | `oh-my-pm.config.json` |

## Canonical commands

| Role | Command |
| --- | --- |
| CLI | `ohmypm` |
| MCP stdio server | `ohmypm-mcp` |
| Release-bundle installer | `ohmypm-install` |

## Compatibility aliases

`oh-my-pm`, `oh-my-pm-mcp`, and `oh-my-pm-install` continue to work.

Each alias is a wrapper over the same implementation in the same process, so
arguments, stdin, environment, working directory, exit code, and signal behavior
are all forwarded unchanged. No application logic is duplicated, and an alias
cannot recurse into its canonical counterpart.

The deprecation warning goes to **stderr, and only stderr**:

```console
$ oh-my-pm status
Warning: `oh-my-pm` is a deprecated compatibility alias.   ← stderr
Use `ohmypm` instead.                                      ← stderr
OH MY PM status: healthy                                   ← stdout
version: 0.5.0
kernel: 0.5.0
```

This matters for two machine-readable contracts:

- **JSON output stays valid.** `oh-my-pm status --json | jq .` still works,
  because the warning never reaches stdout.
- **MCP stdout stays protocol-safe.** stdout carries JSON-RPC framing, where one
  stray byte desynchronizes the client handshake, so `oh-my-pm-mcp` writes its
  warning to stderr before connecting the transport.

An alias prints the same help as its canonical counterpart, and that help shows
`ohmypm`. The aliases never appear in help output, README examples, generated
configuration, or installation instructions.

## No data migration

Project Brain schema stays at **1**. Project Memory store format stays at **2**.
Nothing is moved, copied, or rewritten because a command name changed. An existing
store keeps working exactly as it did under v0.4.

## MCP configuration

Newly generated configuration invokes the canonical command:

```json
{
  "mcpServers": {
    "oh-my-pm": {
      "command": "/absolute/path/to/prefix/bin/ohmypm-mcp",
      "args": []
    }
  }
}
```

The server **key** remains `oh-my-pm`: it is a product identity, not a command,
so an existing configuration keeps its key and only the `command` value needs
regenerating.

An existing configuration that invokes `oh-my-pm-mcp` keeps working through the
compatibility alias. Where the CLI inspects configuration it reports such an entry
as legacy-but-functional and recommends regeneration — never as broken. OH MY PM
does not rewrite a configuration file you own; `ohmypm mcp-config` prints and you
paste.

## Installation

A v0.5 installation creates the canonical commands plus the compatibility
shims — eight files, a POSIX and a Windows `.cmd` launcher for each command:

```text
<prefix>/bin/ohmypm
<prefix>/bin/ohmypm.cmd
<prefix>/bin/ohmypm-mcp
<prefix>/bin/ohmypm-mcp.cmd
<prefix>/bin/oh-my-pm
<prefix>/bin/oh-my-pm.cmd
<prefix>/bin/oh-my-pm-mcp
<prefix>/bin/oh-my-pm-mcp.cmd
```

### Upgrading from v0.4

A prefix installed by v0.4 has only the four `oh-my-pm` shims. Because those
differ from what v0.5 writes, the installer **blocks** the apply with
`shim_content_mismatch` instead of overwriting them — the existing safety gate,
unchanged. Rerun with `--force` once you have confirmed the shims are the ones
OH MY PM installed:

```bash
ohmypm-install --prefix "$HOME/.local" --apply --force
```

Afterwards all six commands work and no orphaned shim remains.

### Uninstall

There is still no uninstall command. Remove the eight shim paths listed above (a
v0.4 installation has only the four `oh-my-pm` ones) and then
`<prefix>/lib/oh-my-pm/`. See [Getting started](../getting-started.md#uninstall).

## Release line

- Release line: `v0.5`
- Bundle profile: `ohmypm-cli-namespace`

The profile is new rather than a reuse of v0.4's `project-brain-timeline`, so a
verifier can distinguish a bundle that ships both command families from one that
ships only the old names. The runtime surface it declares is identical to v0.4:

- twelve read-only MCP tools, zero write tools;
- four CLI project workflows and four GitHub workflows;
- seven `memory` subcommands;
- Project Brain schema 1, store format 2, no migration required;
- stdio transport, network disabled by default with one opt-in read-only
  GitHub provider.

`RELEASE.json` declares `canonicalCommands` and `legacyAliases` as distinct
fields, plus `commandsDeprecatedSince` and `commandRemovalScheduled`, so no reader
can mistake a deprecated alias for a primary command. Previously published
profiles keep resolving; an unknown profile still fails closed.

## Deprecation policy

- Deprecated since: **0.5.0**
- Removal scheduled: **no**

No removal version is announced. If one is ever scheduled it will be announced in
a release ahead of time.

## Non-goals

v0.5 explicitly does **not** include:

- **any Dashboard implementation** — no dashboard work is part of this release;
- a product, repository, package, or environment-variable rename;
- any new CLI command, subcommand, option, or output mode;
- any change to command behavior, JSON schemas, output contracts, storage
  formats, project-memory formats, MCP protocol behavior, or public APIs;
- any storage or data-format migration;
- any registry publication — the workspace packages remain private.
