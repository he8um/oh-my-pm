## Repair apply

Run only against constructed corrupt fixtures.

- **Writer lock, rescan, stale-plan rejection.** `applyRepair` acquires the writer
  lock, re-scans under it, and refuses a plan whose store fingerprint moved —
  before any write, so a stale plan mutates nothing.
- **Exact corrupt bytes preserved in quarantine.** A truncated snapshot record
  with SHA-256 `e198dbd935851218b65296110b082958c2dd8ded493029b7ca14493cf615827c`
  was isolated to
  `quarantine/<operationId>/<digest>/payload.bin`, whose SHA-256 is identical.
- **Quarantine metadata is sanitized.** `metadata.json` and `receipt.json` carry
  store-relative paths, digests, an operation id, and a timestamp. No absolute
  path, host detail, or credential appears in either.
- **Quarantine is physically confined** under the project's own directory inside
  the store.
- **Quarantine is excluded from normal history.** Neither `memory history` nor
  `memory timeline` references quarantined material; after repair, `status`
  reports `healthy` with the surviving snapshots.
- **Isolation is never reported as recovery.** Output distinguishes
  `reconstructed` from `isolated (quarantined, not recovered)` and tallies them
  separately.
- **Derived structures are rebuilt only from verified records.** A store whose
  record was replaced by a symlink to a file outside the store was classified
  `missing_referenced_record` and repaired by `rebuild_derived_manifest` — the
  link was not followed.
- **Repeated apply is idempotent.** A second `--apply` on an already-repaired
  store reported 0 findings and performed 0 actions, leaving all store data
  unchanged. It writes a new receipt for the no-op invocation; receipts are
  per-invocation by design, so this is idempotence of store data, not of the
  receipt directory.
- **Project source files remain unchanged.** A recursive digest of the fixture
  project tree was identical before and after apply.

### Cross-process exclusion

Two `repair --apply` processes were launched concurrently against the same corrupt
store. One acquired the lock and repaired all four damaged records; the other was
rejected with `OMP-MEM-1003` (`storeLocked`, exit `4`). The store was not
concurrently mutated.

### Physical confinement

Writes are confined to the resolved store root. Verified rejections and
containments:

- A **relative** `--data-dir` is rejected: "the project root boundary must be an
  absolute path".
- A **relative** project root is rejected (`OMP-MEM-1001`).
- **Project root equal to the data directory** is rejected (`OMP-MEM-1002`,
  `pathEscape`) — project and data must stay separate.
- A **symlink planted inside the store**, pointing at a file outside it, was not
  followed: the outside file was byte-identical and still present after apply.
- When `--data-dir` itself is a symlink, a nested symlink, a traversal path, or a
  nonexistent leaf, the store is created at the **resolved** location and all
  writes stay within `<resolved-root>/project-brain/**`. A pre-existing unrelated
  file alongside that root was never read, modified, or removed. This is the user
  designating a store location, not an escape.

**Residual platform limitation.** Confinement is enforced by resolving and
validating paths before writing. This does not amount to complete elimination of
TOCTOU races: an adversary able to replace a path component between validation and
write, on a filesystem without atomic protection for that sequence, remains outside
what these checks can guarantee. Windows junction and reparse-point behavior is
covered only to the extent the platform's own path resolution reports it. The
guarantee claimed here is confinement of writes to the resolved store root under
normal operation, not a hardened multi-tenant security boundary.

## Evidence and test defects corrected before publication

Three defects were in the **evidence**, not the shipped behavior. All were found
and corrected before `v0.6.2` was published; none reached the release.

- **Windows root causes.** The integrity suites initially failed on Windows for
  two distinct reasons: repair paths were joined with a hardcoded separator
  (`db40d0a` joins with the platform separator), and the in-memory filesystem
  double was separator-sensitive (`ba9341e`). A further fix resolved the layout
  root so confined paths compare correctly (`84b3285`), and the repair and bounds
  fixtures were routed through the double's own normalizing helpers (`d488c0c`,
  `d7568fd`). The blocker was recorded while open (`93e7c0f`) rather than left
  silent, then closed. Windows qualification passes in the release run.
- **Invalid mutation-filter incident.** A mutation round was invalidated because
  Vitest filters are literal, not regular expressions — a `|` alternation pattern
  matched no tests and exited non-zero, so the round proved nothing. The round was
  rerun with valid filters.
- **Vacuous assertion incident.** A recovery-residue assertion could pass without
  exercising the condition it claimed to check; `a6876f2` made it non-vacuous, and
  `b63fe84` stabilized the resulting baseline.
- **Intermittent baseline incident.** The integrity suite baseline was
  intermittent before being stabilized (`b63fe84`), so a green run was not yet
  trustworthy evidence. Heavy suites are separated from the parallel unit project
  in the Vitest workspace to keep this from recurring.

These were corrected in the implementation branch before the release ran. The
published artifact was qualified only after all of them were closed.

## Rollback and fix-forward policy

`v0.6.2` introduces no store format change and requires no migration, so a user
may return to `v0.6.1` by reinstalling that release; stores written under `v0.6.2`
remain readable by `v0.6.1` because the format is unchanged. Quarantine
directories created by `repair --apply` are inert to older versions.

The published tag and release are immutable: a defect found in `v0.6.2` is
addressed by **fix-forward** in a subsequent patch release, never by moving the
tag, replacing an asset, or deleting the release.
