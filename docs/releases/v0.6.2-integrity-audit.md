# v0.6.2 Project Memory integrity audit

Audit of the Project Memory integrity guarantees as they exist at
`ed9299e33e437f80043255c84f4e09675da82a4d` (post-v0.6.1 `main`), performed before
any v0.6.2 implementation work.

**Why this document exists first.** The original v0.6.2 scope was written as if
atomic writes, integrity metadata, migrations, locking, path confinement, and
privacy enforcement all needed building. They do not — most of them shipped
earlier and are genuinely implemented, not stubbed. Building a second atomic-write
layer beside a correct one would make the system worse, so the release was
re-scoped to **verification and gap closure** and this audit is the authority for
what that means.

Baseline at audit time: **116 tests across 13 suites** in `project-memory/test`,
all passing.

## Status vocabulary

| Status | Meaning |
| --- | --- |
| **Proven** | Implemented, and a test would fail if the guarantee broke. |
| **Under-proven** | Implemented and believed correct, but no test pins the guarantee. |
| **Partial** | Some of the guarantee exists; a named part is absent. |
| **Missing** | No implementation. |
| **Out of scope** | Deliberately excluded, with a reason. |

## Confirmed material gaps

Five gaps are real, evidence-backed, and each changes the confidence of a shipped
guarantee. They are the whole of the v0.6.2 implementation scope.

### G1 — Fault injection cannot reach inside the atomic write (item 3)

The seven fail points are all at the commit-sequence level. `writeFileAtomic` is
a single opaque step, so four required stages cannot be tested at all:
before temp write, during temp write, after flush, before parent sync.

The write may well be correct; nothing proves it. **Fix:** extend the fail-point
enumeration into the filesystem port so injection can occur inside the write, and
add the missing stage tests. Do not replace `writeFileAtomic`.

### G2 — Post-crash recovery is untested, and one test misreports itself (item 15)

`store-commit.test.ts:125` creates `new MemoryFileSystem()` for the follow-up
commit — a pristine filesystem with no lock file, no staging residue, no partial
state. The genuine property (a later write against the *same damaged* store
succeeds) is unverified.

This is the most misleading finding in the audit: the test reads as if crash
recovery is covered. **Fix:** reuse the crashed filesystem, and assert the lock is
gone, residue is detectable, and the next commit succeeds.

### G3 — Locking is never exercised across real processes (item 7)

The stale rule (age AND dead owner) is correct and must not be weakened. But the
lock's real contract is `open(path, "wx")` on a real filesystem between real
processes, and every existing test is in-process against an in-memory port.

**Fix:** add separate-process contention tests using the real Node adapter —
two processes cannot both write, a live slow writer is never evicted, a dead
stale owner is reclaimed, acquisition is bounded, crash residue recovers.

### G4 — Path confinement is lexical, and writes are less protected than reads (item 8)

Containment never consults the filesystem, so a symlink or junction inside the
data root pointing outside satisfies `isSameOrInside`. Reads mitigate this by
refusing symlinks at the leaf; the write path performs no such check.

Severity is bounded — managed paths are SHA-256-derived under a confined root, so
exploiting this needs prior write access to the store — but the read/write
asymmetry is a genuine inconsistency. **Fix:** add junction, reparse-point,
nested-symlink, and case-insensitive coverage; close the write-path asymmetry if
the tests confirm it is reachable.

### G5 — Corruption can be detected but never isolated or repaired (items 9, 10)

Detection is strong and deliberately non-destructive. But a user with a corrupt
record has no supported path forward: no quarantine, no preview, no repair.

**Fix:** preview-first quarantine that isolates a corrupt record, preserves it as
evidence, and keeps the remaining valid history readable. Never delete or
overwrite an authoritative record. Extend the existing memory command surface only
if a public command is justified; otherwise keep it internal and say so.

## Non-gaps — do not "fix" these

- **Atomic write mechanism.** Temp → fsync → rename with `0600` and best-effort
  directory fsync is correct. The gap is provability, not design.
- **Stale-lock rule.** Requiring age **and** a dead owner avoids evicting a live
  slow writer. Do not relax it to simplify a test.
- **No auto-repair on read.** Deliberate and proven. Reads must never mutate.
- **No cache.** Nothing needs one.
- **No auto-pruning.** The non-destructive default is correct; it needs a test,
  not a change.
- **Prefix containment.** `relative()` + `..` already avoids the string-prefix
  bug.
- **Domain-separated digests.** Distinct domain constants per record kind already
  prevent cross-context digest reuse.

## Release justification

The re-scoped release threshold requires at least one material integrity or
verification gap whose closure changes the confidence of the shipped system.

**Met.** G2 is a test that misreports what it proves; G3 leaves the cross-process
contract of a single-writer lock unverified; G1 makes four of nine required crash
stages untestable; G5 leaves users with no recovery path from a detected
corruption. Each changes what can honestly be claimed about the system.

## Deferred, with reasons

- **Cache policy (item 11)** — no cache exists and none is needed.
- **Full performance architecture** — v0.6.5. This release records bounded
  behaviour baselines only, and invents no SLOs.
- **New schema version** — explicitly not invented to exercise the migration
  framework; `migration1to2` and historical fixtures already exercise it.
- **Stale `README` / `SECURITY.md` validator gap** — `validate-doc-truth` does not
  check the README badge block, which is how a `v0.5.3` latest-stable claim
  survived three releases. Corrected in the v0.6.1 truth PR, but the *validator*
  gap remains and is recorded as separate future work, not mixed into this
  release.
