# OH MY PM — v0.5.1 Maintenance Scope

> **Status: scope locked.** v0.5.1 is a **patch** release that fixes two
> confirmed architectural problems and changes **no public behavior**.
>
> 1. Active documentation no longer reflected the actual repository and product
>    state.
> 2. Shared application logic was concentrated inside the CLI package, creating
>    an unsuitable dependency boundary for a future third interface.
>
> v0.5.1 adds **no** feature, **no** command, **no** MCP tool, **no** schema
> change, **no** store-format change, **no** migration, and **no** network path.

## Why this is a patch release

Everything a user can observe is unchanged from v0.5.0:

| Surface | v0.5.1 |
| --- | --- |
| Canonical commands | `ohmypm`, `ohmypm-mcp`, `ohmypm-install` — unchanged |
| Compatibility aliases | `oh-my-pm`, `oh-my-pm-mcp`, `oh-my-pm-install` — unchanged, no removal scheduled |
| CLI grammar, defaults, exit codes | unchanged |
| CLI JSON and Markdown output | unchanged |
| MCP tools | twelve read-only, zero write, exact same order |
| MCP schemas and annotations | unchanged |
| Project Brain schema | `1` |
| Project Memory store format | `2` |
| Storage paths | unchanged |
| Migration required | none |
| Release line / bundle profile | `v0.5` / `ohmypm-cli-namespace` |

The internal package structure and the documentation change. The externally
observable behavior does not.

## Problem 1 — documentation drift

The repository shipped five release lines while parts of its active
documentation stayed frozen at v0.2 and v0.3. The drift is not cosmetic: it
makes materially false claims about what the code does.

The worst offenders were claims that inverted reality:

- `project-memory/README.md` — "Nothing invokes it yet", while the package backs
  seven CLI subcommands and two MCP tools and ships in the release bundle.
- `runtime/src/index.ts` — a comment stating "no CLI or MCP surface invokes the
  Project Brain Runtime", which would lead a maintainer to read shipped code as
  dead code.
- `installer/README.md` — "does not write files ... Real filesystem installation
  will be added in a later phase", while `ohmypm-install` performs real
  transactional prefix writes.
- `README.md` — "the repository build of the `0.3.1` source line", contradicting
  its own masthead, plus a ten-tool MCP claim and a "planned architecture".
- `mcp-server/README.md` — eleven tools, with `project_timeline` absent entirely.

### Rule applied

Active documents describe the current state and were corrected. **Historical
documents were left alone.** `docs/releases/**`, `docs/v0.3/**`,
`docs/architecture/v0.2-stabilization-audit.md`, and superseded `CHANGELOG.md`
entries are point-in-time records; their old version numbers and tool counts
were true when written and remain historically accurate.

Correctness is enforced by `pnpm validate:docs`
([`tools/validate-doc-truth.mjs`](../../tools/validate-doc-truth.mjs)), which
derives its expectations from canonical sources — `version.json`,
`command-surface.json`, package manifests, the MCP tool registration constants,
and the memory subcommand constants — rather than introducing a second source of
truth.

## Problem 2 — application logic owned by the CLI

Before v0.5.1, `@oh-my-pm/cli` owned far more than a CLI adapter:

- local project document loading and project configuration,
- runtime request construction and Runtime composition,
- provider diagnostics orchestration,
- Project Memory process orchestration,
- Node-specific filesystem boundaries.

`@oh-my-pm/mcp-server` therefore depended on `@oh-my-pm/cli` to reuse that
logic:

```text
MCP ──> CLI ──> Runtime / Providers / Project Memory
```

That direction is wrong. A second presentation surface should never have to
depend on a first one, and a third — the planned v0.6 local Dashboard — must not
be forced to depend on a command-line package to reach shared use cases.

### Target

```text
CLI ───────────┐
MCP ───────────┼──> Application ──> Runtime / Providers / Project Memory
Future UI ─────┘                    └──> Planner / Skills / Kernel
```

The future UI line is **architectural context only**. v0.5.1 implements no
Dashboard, no HTTP server, and no UI package.

## Architecture decision

**Decision.** Introduce a private workspace package `@oh-my-pm/application` that
owns the reusable application use cases, and reduce CLI and MCP to presentation
adapters over it.

**Alternatives considered.**

1. *Leave the logic in CLI and let the Dashboard depend on CLI.* Rejected: it
   entrenches the inverted dependency and forces a UI to carry argument parsing,
   help text, and process-exit machinery it can never use.
2. *Duplicate the orchestration into MCP and any future surface.* Rejected:
   duplicated orchestration drifts, and parity between surfaces stops being
   structurally guaranteed.
3. *Promote Runtime to own the use cases.* Rejected: Runtime is a deterministic
   request-handling engine below the use-case layer. Folding Node filesystem
   adapters, provider config resolution, and Project Memory process
   orchestration into it would broaden a deliberately narrow contract.

**Consequences.** One new private package and a one-time import migration in two
adapters, in exchange for a dependency direction that admits a third surface
without further restructuring. No runtime cost and no user-visible change.

### Two export surfaces

| Surface | Contents |
| --- | --- |
| `@oh-my-pm/application` | use-case contracts, dependency-injected orchestration, structured errors, shared result types |
| `@oh-my-pm/application/node` | local filesystem adapters, project config and document loading, local Project Memory store construction, environment and config resolution |

Node filesystem objects never leak into domain-level results.

### What the Application package must never do

Enforced by [`tools/validate-boundaries.mjs`](../../tools/validate-boundaries.mjs):

- parse `process.argv`, write to stdout or stderr, or call `process.exit`
- produce CLI help or know executable names
- know MCP JSON-RPC or construct MCP tool responses
- render terminal text or HTML, or start an HTTP server
- depend on CLI, MCP, Installer, or Distribution

## Release lineage

There is **no `v0.5.0` tag and no `v0.5.0` GitHub release**. The v0.5.0 work was
merged to `main` as PR #22 but never published.

- The latest published stable release is **`v0.4.0`**, and it remains the
  immutable base of the lineage.
- v0.5.1 **supersedes the unpublished 0.5.0 source candidate**.
- If published, v0.5.1 would be the first published stable artifact of the v0.5
  line.

No `v0.5.0` tag is invented, and no existing release tag is moved, replaced,
recreated, or deleted. Merging the v0.5.1 pull request publishes nothing.

## Non-goals

v0.5.1 implements none of the following: Dashboard, web UI, HTTP server, REST or
GraphQL API, React, Vite, Tauri, Electron, PWA, browser launch, local port,
multi-project dashboard, background daemon, filesystem watcher, automatic or
scheduled capture, cloud sync, user accounts, telemetry, remote analytics, a new
provider, GitHub mutation, a new CLI command, a new MCP tool, HTTP MCP
transport, a Project Brain schema change, a Project Memory format change, a
storage migration, compatibility alias removal, or npm publication.

**The Application package is the foundation for v0.6, not the v0.6 Dashboard.**
