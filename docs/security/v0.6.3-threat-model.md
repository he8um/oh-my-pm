# v0.6.3 Threat Model — Security and Trust Boundaries

Audit performed against commit `6c31480258bc232ebe007d911cfbfd92dc1a180b`, on the
immutable `v0.6.2` base. This document is an **audit record and planning input**.
It is informative, not normative: [`docs/security-model.md`](../security-model.md)
remains the normative statement of the security model, and nothing here changes
it. No finding below has been remediated; remediation is planned in
[`v0.6.3-implementation-plan.md`](v0.6.3-implementation-plan.md).

The source version stays `0.6.2`, published. No code, test, dependency,
workflow, version, or release-state value was changed by this audit.

## Method, and why it produced a short list

Every claim below is grounded in a file and line that was read. Where a control
is asserted, the implementing code was located; where a gap is asserted, the
search that failed to find a control is named, so a reader can repeat it. A
control that exists only in documentation is recorded as documentation, not as a
control.

The result is deliberately unflattering to the audit rather than to the
codebase: the great majority of what a security review would normally propose to
build **already exists and is correct**, and is enforced by CI rather than by
convention. This repeats the pattern recorded for `v0.6.2`, whose scope was
rewritten after an audit found most of the proposed work already done
(`ROADMAP.md`). Accordingly this model spends most of its length establishing
what is already true — because an invariant that is real but unrecorded is the
thing most likely to be broken by a future change — and concentrates its
findings on a small number of genuine gaps.

Two findings are novel and were confirmed twice by independent inspection: the
MCP read-only annotation gap (F-01) and the unsigned release trust chain (F-02).

## Protected assets

| Asset                   | Where it lives                           | Why it matters                                                                     |
| ----------------------- | ---------------------------------------- | ---------------------------------------------------------------------------------- |
| The analyzed project    | The user's working tree                  | Read-only by contract. A write is a breach of the product's central promise.       |
| Project Brain memory    | `<data-root>/project-brain/v1/`          | The user's only copy of captured history. Corruption or deletion is unrecoverable. |
| `OH_MY_PM_GITHUB_TOKEN` | Process environment only                 | A leaked token grants the attacker the user's GitHub read scope.                   |
| The MCP protocol stream | `stdout` of the MCP server               | A single stray byte breaks the JSON-RPC framing for the connected agent.           |
| The release artifact    | GitHub Release assets                    | Every installing user executes it.                                                 |
| The installed prefix    | `<prefix>/bin`, `<prefix>/lib/oh-my-pm/` | Shims are on the user's `PATH`.                                                    |

## Actors and trust levels

| Actor                      | Trust                | Capability                                                                                                                                 |
| -------------------------- | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| The local user             | Trusted              | Runs the CLI; supplies argv, env, and a project root. Already able to run arbitrary code as themselves.                                    |
| Project documents          | **Untrusted**        | Markdown and `oh-my-pm.config.json` in the analyzed project. May be authored by anyone whose PR was merged, or cloned from a hostile repo. |
| GitHub API responses       | **Untrusted**        | Issue and PR bodies, titles, comments, review text. Attacker-controlled on any public repository.                                          |
| The connected MCP agent    | **Semi-trusted**     | An LLM. Supplies tool inputs derived from untrusted context; may be prompt-injected by the documents it just read.                         |
| A co-located local process | **Untrusted**        | Same-UID process racing the store or the install prefix.                                                                                   |
| The release pipeline       | Trusted-by-necessity | GitHub Actions runners and the third-party actions they execute.                                                                           |
| A network attacker         | **Untrusted**        | TLS-bounded; may attempt redirect or oversized-response abuse.                                                                             |

Note the actor that matters most and is easiest to overlook: the **MCP agent is
not the user**. It is a program that has just read untrusted documents and may
be acting on instructions embedded in them. Every MCP input is therefore treated
as untrusted in this model even though the user launched the server.

## Entry points

1. CLI argv — `cli/bin/{omp,ohmypm,oh-my-pm}.mjs`, parsed in `cli/src/parser.ts` and `cli/src/memory-parser.ts`.
2. Environment — 7 variables, 3 read sites (enumerated below).
3. Project documents — `application/src/node/project-documents.ts`.
4. Project configuration — `oh-my-pm.config.json`, `application/src/node/project-config.ts`.
5. Provider configuration — `providers.json`, `application/src/node/provider-config.ts`.
6. MCP tool inputs — 12 zod-validated schemas, `mcp-server/src/server.ts`.
7. GitHub API responses — `providers/src/github/transport.ts`.
8. The on-disk store — read back by `project-memory/src/store.ts`; may have been mutated out-of-band.
9. The release bundle — consumed by `distribution/libexec/release-install-core.mjs`.

## Trust boundaries

- **B1 Process boundary.** argv, env, clock, and pid enter only at `cli/bin/*.mjs` and `mcp-server/bin/*.mjs`. Enforced by per-package purity tests (`cli/test/purity.test.ts:84-90` iterates every `cli/src/*.ts` against 37 forbidden markers including `process.env`, `fetch(`, `child_process`, `new Date`).
- **B2 Filesystem read boundary.** Only `application/src/node/**` may import `node:*` (`application/test/boundary.test.ts:200-206`), and even there **no write API is permitted** (`:231+`).
- **B3 Application-data write boundary.** Only `project-memory` writes, only under a confined data root, separated from the project root both ways (`project-memory/src/path-safety.ts:assertProjectDataSeparation`).
- **B4 Network boundary.** Only `providers/src/github/transport.ts` may reach the network; `fetch(`/`AbortController`/`api.github.com` outside it is a build error (`tools/validate-boundaries.mjs:2680-2688`).
- **B5 MCP protocol boundary.** `stdout` is reserved for JSON-RPC; the three bin wrappers may not touch it (`tools/validate-boundaries.mjs:716-744`).
- **B6 Release integrity boundary.** The bundle is verified before, during, and after install (`release-install-core.mjs`).

## Existing controls worth recording as invariants

These are real, verified, and currently unrecorded as _measurable_ invariants —
which is the actual risk they carry.

- **Deny-by-default argument parsing.** Closed command set; unknown `--option` rejected terminally (`cli/src/parser.ts:370-372`); option values may not look like options; duplicates rejected; every scalar anchored-regex plus range bounded.
- **No security-relevant environment switch exists.** Grepped for `*_SKIP_*`, `*_DISABLE_*`, `*_INSECURE*`, `*_UNSAFE*`, `NODE_TLS_REJECT_UNAUTHORIZED`, `*_API_URL`, `*_BASE_URL`: **none**. There is no way to turn a check off, change the API origin, or pass a token by flag — `--token` is a build-breaking forbidden marker (`tools/validate-boundaries.mjs:2645`).
- **Token containment, not redaction.** There is no redaction function anywhere, by design: the token exists only as a closure variable and one outbound header (`providers/src/github/transport.ts:111-124`). It is read behind validation, so controlled failures never touch it (`application/src/node/deps.ts:146-178`). Output carries a 3-state presence enum, never a value (`provider-diagnostics.ts:161-164`). Proven by 26 non-leakage assertions across 6 packages. Containment is stronger than a pattern list, which is why no pattern list should be introduced.
- **Provider config is hardened at the read.** `lstat` never `stat`, symlinks rejected not followed (`provider-config.ts:214-246`); size checked against `stat.size` _before_ read (64 KiB); exactly one candidate path, no parent search; secret-marker keys rejected first at all three levels (`providers/src/config.ts:58-70, 96-108`); `SyntaxError` discarded so source text is never echoed.
- **Repair is explicit and evidence-preserving.** `apply !== true` refuses (`project-memory/src/repair-apply.ts:148-151`); the original bytes are quarantined and digest-confirmed _before_ removal (`:322-325`); quarantine is never pruned (`path-safety.ts:31-49`).
- **Release verification is mandatory and unskippable.** No env read in the installer core (grep: zero `process.env`); `--force` overrides drift only, never source validation (`release-install-core.mjs:780-783, 1087`); rollback is gated on exact-state re-verification of manifest, all 12 shims, modes, and full SHA-256 tree (`:911-977, 1292-1301`).
- **Archives are byte-reproducible, enforced in CI** by a double build and byte comparison (`tools/check-release-archive-reproducibility.mjs:92-101`).
- **Least-privilege CI.** All 12 workflows declare `permissions:` explicitly; every default is `contents: read`; `contents: write` appears only on environment-gated publish jobs; no `pull_request_target`, no `actions/github-script`, no repository secrets, no automated `npm publish`.

## Findings

Nine findings. **Zero Critical, zero High.** The absence of a High is a finding
in itself and is stated plainly rather than manufactured: the local trust
boundaries are held by code and by CI, and the one systemic weakness (F-02/F-03)
sits in the trust chain _above_ the product, where the threat requires
repository-write or third-party-action compromise.

Severity reflects exploitability under this model's actor set, not theoretical
worst case.

### F-01 — Medium — 10 of 12 MCP tools advertise no read-only annotation

**Component.** `mcp-server/src/server.ts`, `tools/check-mcp-server.mjs`

**Evidence.** `annotations:` appears exactly twice in `mcp-server/src/server.ts`
(lines 1375 and 1407) — only `project_changes` and `project_timeline` declare
`readOnlyHint: true`. The other ten registrations pass no `annotations` object.
The smoke check that is supposed to guarantee the read-only surface tests the
wrong condition:

```js
// tools/check-mcp-server.mjs:168-178
const annotations = tool.annotations ?? {};
if (annotations.destructiveHint === true) { ... }
if (annotations.readOnlyHint === false) { ... }
```

An absent annotation satisfies both branches. The comment at `:165-167`
acknowledges the tools have no annotations and treats that as acceptable, so the
check passes by construction and can never fail for the ten. Meanwhile
`docs/security-model.md` states "twelve read-only tools and **zero** write
tools", and each tool's own `description` says it never modifies files.

**Impact.** No write capability exists, so this is not a privilege escalation —
it is a **missing machine-readable assertion of the product's central MCP
promise**. An MCP client that gates tool use on `readOnlyHint` (a documented
reason for the annotation to exist) cannot confirm read-only status for ten of
twelve tools and must fall back to parsing English descriptions. The deeper
problem is the false assurance: a future tool registered _with_
`readOnlyHint: false` omitted, or with a genuine write path, would pass
`check-mcp-server.mjs` unchanged. The guard cannot detect the thing it exists to
detect.

**Remediation.** Add explicit `annotations: { readOnlyHint: true,
destructiveHint: false, idempotentHint: true, openWorldHint: <false for local,
true for GitHub> }` to all ten. Then invert the check to require
`readOnlyHint === true` and `destructiveHint === false` on **every** tool, so
absence fails.

**Verification.** `pnpm mcp:smoke` fails when any tool omits `readOnlyHint`;
a unit test asserts all 12 registrations carry it; `openWorldHint` correctly
distinguishes the 4 network-reaching GitHub tools from the 8 local ones.

### F-02 — Medium — Release integrity is trust-on-first-use; no signature or attestation exists

**Component.** `.github/workflows/release-v0.6.yml`, `tools/release-archive-utils.mjs`, `tools/release-bundle-utils.mjs`

**Evidence.** Grepped `cosign`, `sigstore`, `slsa`, `attest`, `attestation`,
`gpg`, `--sign`, `provenance`, `minisign`, `openpgp`, `id-token` across
`.github/`, `tools/`, `distribution/`, `installer/`: **no match** for any signing
mechanism. No workflow declares `permissions: id-token: write`. The only
"provenance" hits are an unrelated domain term in `ApplicationResult` source
descriptors. `installer/README.md:72` is explicit and honest: "The current
signature is a deterministic placeholder... No signing keys are generated, read,
stored, or used" — and that placeholder is not wired into the release path at
all (`tools/install-release-bundle.mjs:11-16` imports only from
`release-install-core.mjs`).

Integrity therefore rests on two unsigned checksum files. The in-bundle
`SHA256SUMS` lives inside the bundle it describes and excludes itself
(`release-bundle-utils.mjs:935`); the external
`oh-my-pm-vX.Y.Z-SHA256SUMS.txt` is a Release asset alongside the archives it
names.

**Impact.** An attacker who can write the GitHub Release replaces all three
assets and regenerates both checksum files; every one of the installer's four
verification passes then validates a wholly attacker-authored bundle _correctly_.
The verification is not defective — it is faithfully checking internal
consistency, which is all an unsigned checksum can establish. There is no
cryptographic tripwire and no way for a user to attribute a bundle to this
repository's pipeline. Given the installed shims land on `PATH`, the consequence
of a successful substitution is local code execution.

Rated Medium rather than High because the precondition is repository-write or
Release-write access, which already implies substantial control; the finding is
about **detectability and attribution**, not about opening a new path.

**Remediation.** Add `actions/attest-build-provenance` to the publish job with
`id-token: write` scoped to that job only, publishing an attestation over all
three assets. Document `gh attestation verify` as the user-facing check. This
does not require a key of the maintainer's own.

**Verification.** A published release carries a verifiable attestation;
`gh attestation verify` succeeds against genuine assets and fails against a
locally modified copy; the added permission is scoped to the publish job and no
other workflow gains `id-token`.

### F-03 — Medium — No GitHub Action is SHA-pinned; one is pinned to a mutable branch

**Component.** all 12 workflows in `.github/workflows/`

**Evidence.** `grep -rn "uses:.*@[0-9a-f]\{40\}" .github/workflows/` → **zero
matches.** The full external set: `actions/checkout@v5`,
`actions/setup-node@v5`, `actions/upload-artifact@v4`/`@v7`,
`actions/download-artifact@v4`/`@v7`, `pnpm/action-setup@v4.4.0`, and
`dtolnay/rust-toolchain@stable`. The last resolves to whatever the branch HEAD
is at job start and runs in the release path (`release-v0.6.yml:176`), not only
in CI. The artifact-version inconsistency (`@v4` vs `@v7` for the same action
across workflows) indicates the refs drift unnoticed.

**Impact.** A compromised or force-pushed third-party action executes inside the
job that produces the release bundle. Combined with F-02, a poisoned artifact
carries no signature that would reveal the substitution, and the installer would
verify it as internally consistent. This is the highest-leverage unmitigated
path in the audit, and it is also the cheapest to close.

**Remediation.** Pin every `uses:` to a full 40-character commit SHA with the
human-readable version in a trailing comment. Reconcile `upload-artifact` /
`download-artifact` to one version. Optionally add Dependabot
`github-actions` updates so pins are maintained rather than frozen.

**Verification.** A CI step (or `actionlint`/`zizmor`) fails on any `uses:` not
matching `@[0-9a-f]{40}`; all release workflows build and publish unchanged
after pinning.

### F-04 — Low — The shipped bundle verifier skips every symlink

**Component.** `tools/check-release-bundle.mjs`

**Evidence.**

```js
// tools/check-release-bundle.mjs:86
if (entry.isSymbolicLink()) continue;
```

`grep -n "symlinkEscapes\|escapes bundle" tools/check-release-bundle.mjs` → no
match, whereas the _build-time_ enumerator does check escape
(`release-bundle-utils.mjs:750-751`). Because this verifier is the one **shipped
inside every bundle** and re-executed at install time
(`release-install-core.mjs:642-649, 1220-1236`), symlinks are invisible to it for
both the escape check and the `SHA256SUMS` completeness check — and the writer
excludes symlinks from `SHA256SUMS` too (`release-bundle-utils.mjs:935`).

**Impact.** Bounded. The installer independently scans the source bundle and the
staged copy for escaping and dangling symlinks (`release-install-core.mjs:561-573`,
`1047-1071`), so a _malicious_ escape is still caught. What is uncovered is an
added or retargeted in-bundle symlink that stays inside the root: it produces no
checksum reason from either side. Defence-in-depth is thinner than the layering
implies.

**Remediation.** Make the shipped verifier enumerate symlinks, assert each
resolves inside the bundle root, and cover link targets in the integrity check.

**Verification.** A negative test plants an escaping symlink, a dangling
symlink, and an inside-root symlink in a fixture bundle and asserts the shipped
verifier rejects the first two and accounts for the third.

### F-05 — Low — Bundle-level checksum tampering has no test

**Component.** `distribution/libexec/release-install-core.test.mjs`, `tools/`

**Evidence.** `grep -rn "sha256sums_checksum_mismatch\|sha256sums_unlisted_file\|sha256sums_lists_missing\|sha256sums_malformed" --include="*.test.mjs"` → **zero
matches repo-wide.** These are the four strongest integrity reasons in
`release-install-core.mjs:603-617`. Archive-level mismatch _is_ tested
(`tools/check-release-archives.test.mjs:134`) and `sha256sums_missing` is tested
(`release-install-core.test.mjs:352`), so the omission is specifically the
tamper cases: a wrong digest, an unlisted extra file, a malformed line.

**Impact.** No live exposure — the code paths were read and are correct. The risk
is regression: the primary integrity gate for the local install path is
unprotected by any test, so a refactor could silently weaken it.

**Remediation.** Add negative tests that flip a byte in a listed file, add an
unlisted file, and corrupt a `SHA256SUMS` line, asserting each specific reason
code.

**Verification.** Each of the four reason codes is asserted by at least one
test; mutating the comparison in `release-install-core.mjs` fails the suite.

### F-06 — Low — Rollback is best-effort, deletes its own backups, and is untested

**Component.** `distribution/libexec/release-install-core.mjs`

**Evidence.** Every step of `restoreBackups` is wrapped in `try {} catch {}`
(`:1154-1187`, commented "best-effort" five times), so a failed restore is
swallowed and the caller receives only `post_install_verification_failed`.
`cleanupTempOnly()` runs immediately after `restoreBackups()` (`:1294-1295`) and
backups live inside `txDir` — so if a rename back fails, the backup is then
deleted. No test forces a post-install verification failure: I read all 34 test
titles in `release-install-core.test.mjs` and all 16 in
`tools/release-install-e2e.test.mjs`; the nearest is `:177`, which exercises the
happy `--force` replace path. `grep -rniE "uninstall|rollback|revert"` over
`tools/`, `distribution/`, `cli/` finds only comments; there is no uninstall
command.

**Impact.** A rollback that partially fails leaves the prefix in a mixed state,
reports nothing about it, and may have destroyed the only copy of the previous
install. Reachable only after an already-failing install.

**Remediation.** Preserve backups until after a successful restore; verify the
restored state and surface a distinct reason code when restore itself fails; add
fault-injection tests around the rollback path.

**Verification.** A test forces post-install verification failure, asserts the
prefix returns to its exact prior state, and asserts backups survive a failed
restore.

### F-07 — Low — `${{ inputs.version }}` is interpolated into `run:` bodies

**Component.** `release-v0.6.yml` and four earlier release workflows

**Evidence.** `release-v0.6.yml:220, 287, 297, 353, 370` use
`VERSION="${{ inputs.version }}"`, and `:459` does the PowerShell equivalent —
while the same workflow demonstrates the correct pattern at `:105-119`, passing
inputs through `env:` and comparing `"$INPUT_VERSION"`. Same shape in
`release-v0.3-rc.yml`, `release-v0.3.yml`, `release-v0.4.yml`, `release-v0.5.yml`.

**Impact.** Low, for two independent reasons: `workflow_dispatch` requires repo
write access (so the dispatcher already exceeds what injection grants), and the
gate step at `:105-119` runs first and hard-fails unless the value is exactly
the pinned literal. Safety is therefore a property of **step ordering**, not of
construction — fragile under reordering, under an added `if:`, or when a
workflow is copied for the next release line without the gate.

**Remediation.** Drop the interpolation: the version is already hardcoded in
~20 other places in the same file. Where a value is genuinely needed, pass it via
`env:` and reference `"$INPUT_VERSION"`.

**Verification.** No release workflow contains `${{ inputs.` inside a `run:`
block; a dispatch with a shell-metacharacter version is rejected by the gate
before any `run:` uses it.

### F-08 — Low — Predictable transaction directories are recursively removed

**Component.** `release-install-core.mjs:1128, 1195`; `release-archive-utils.mjs:535-539`; `release-bundle-utils.mjs:957`

**Evidence.** `join(productDirectory, ".install-tx-" + process.pid)` followed by
`if (existsSync(txDir)) rmSync(txDir, { recursive: true, force: true })`. Other
tools in the same repo use `mkdtempSync` correctly
(`tools/check-release-archives.mjs:221-222`), so the pattern is inconsistent
rather than deliberate.

**Impact.** A co-located process that can write `<prefix>/lib/oh-my-pm/` can
pre-create the PID-derived path and have it recursively deleted, or race its
contents. Write access to that directory already largely implies control of the
install, which bounds severity.

**Remediation.** Use `mkdtempSync` for all transaction and temp directories.

**Verification.** No release tool derives a temp path from `process.pid`; an
existing directory at a predictable path is never recursively removed.

### F-09 — Informational — Small hygiene gaps that mask drift

Grouped because none is independently actionable but each weakens a guard.

- **Stale allowlist entries.** `tools/validate-boundaries.mjs:1220` allowlists `cli/src/github-token.ts`; `ls` confirms the file does not exist. A stale entry silently narrows enforcement, and a file re-created at that path starts life pre-allowlisted.
- **The privacy key-scan is call-site-invoked, not chokepoint-enforced.** `assertNoForbiddenKeys` is an ordinary function the commit path calls; no CI rule asserts every store write is preceded by it. Unlike the marker scans, a _new_ persistence path that omitted the call would not be caught statically. This is the one place where "could a new code path bypass a control" has a real answer.
- **`mcp-server/src/**` has no stdout ban.** The boundary rule at `tools/validate-boundaries.mjs:716-744` covers only the three bin wrappers. No `console.*` currently exists in `mcp-server/src/` (verified by grep), so the invariant holds today by discipline rather than by enforcement — and stdout cleanliness is exactly the invariant whose breach corrupts the protocol stream.
- **No token shape validation.** `readGitHubTokenFromEnvironment` applies only `trim()` and non-empty. A token containing CRLF reaches a template literal at `transport.ts:121`; Node's HTTP stack rejects it, so the control is delegated rather than local.
- **Unbounded directory recursion in document discovery.** `collectCandidates` (`project-documents.ts:100-139`) has no depth cap. Cycles are impossible (symlinks skipped) and the byte budget bounds reading, but a pathologically deep tree could exhaust the stack. Contrast the privacy scanners, which cap depth at 128.
- **`shell: true` on Windows in the bundle builder.** `release-bundle-utils.mjs:224, 976-982` passes an operator-supplied `--output` into a `cmd.exe` line. Self-inflicted only; the exit code is also deliberately ignored (`:972-974`).

**Remediation.** Assert allowlists are non-stale; extend the stdout ban to
`mcp-server/src/**`; add a charset assertion on the token; cap walk depth;
replace the Windows `shell: true` with a direct executable invocation.

## Residual risks accepted, and stated as such

- **TOCTOU is reduced, not eliminated.** Node exposes no descriptor-relative `openat`/`O_NOFOLLOW`, so a sufficiently privileged concurrent actor can replace an ancestor between validation and the write syscall. The single-writer lock and owner-only `0700` modes bound who can win that race. This is documented at `physical-confinement.ts:33-41` and should stay documented rather than be overclaimed.
- **`memory export --destination` is an intentional user-directed write.** It is bounded _away from_ the project root and the data root, not _into_ an allowed directory (`path-safety.ts:344-356`). Mitigated by must-not-pre-exist, explicit `--apply`, and already-minimized bytes. Recorded as a deliberate capability, not a confined path.
- **`OH_MY_PM_PROVIDER_CONFIG` redirects a filesystem path.** Bounded by what the hardened loader will do with the file (regular file, ≤64 KiB, no symlink, strict schema, no secret keys), not by the path itself.
- **The release trust root is GitHub Release write access.** F-02 improves detectability; it does not remove this dependency.
- **Third-party actions execute in the release path.** F-03 pins them; it does not eliminate reliance on them.
