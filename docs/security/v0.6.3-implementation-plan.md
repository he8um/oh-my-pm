# v0.6.3 Implementation Plan — Security and Trust Boundaries

Planning input for `v0.6.3`, derived from
[`v0.6.3-threat-model.md`](v0.6.3-threat-model.md) at commit
`6c31480258bc232ebe007d911cfbfd92dc1a180b`. Informative, not normative.

Nothing here is implemented. The source version stays `0.6.2`, published, and
`release-state.json` is unchanged. This plan proposes no release.

## Shape of the work, and what it deliberately excludes

The audit found the local trust boundaries already held by code and CI, so this
plan is **not** a build-out. It does three things, in this order of value:

1. **Closes the one control that cannot detect what it exists to detect** (PR-1).
2. **Closes the trust chain above the product**, where the only systemic weakness lives (PR-2, PR-3).
3. **Converts existing correct behaviour into enforced invariants** (PR-4 through PR-9), so a future change cannot quietly remove it.

Category 3 is most of the diff and carries the least behavioural risk — which is
the point. An invariant that holds by discipline is one refactor away from not
holding.

Excluded by scope, and not revisited below: no change to the CLI command surface;
no new MCP tool and no MCP write capability (the surface stays at 12 read-only
tools); no Project Memory schema or format change; no Dashboard, accounts, cloud
sync, telemetry, or remote analytics; no dependency updates; no changes to PRs
`#42`, `#44`, `#45`, `#46`, `#47`; no `release-state.json` edit; no tags,
releases, or publication branches.

Two things the audit found are deliberately **not** changed, because changing
them would make the product worse:

- **No secret-redaction layer is introduced.** The token is contained, never in a value that reaches an output funnel. A pattern-matching redactor would be a weaker control that falls behind new token formats and invites bypass. The invariant to enforce is containment (PR-6), not filtering.
- **The documented TOCTOU residual is not overclaimed.** Node exposes no descriptor-relative primitives; PR-7 measures what the code actually guarantees ("validated immediately before the write against the real filesystem"), not race-freedom.

## Ordering and dependencies

```
PR-1  MCP read-only annotations            (independent)
PR-2  Pin all GitHub Actions to SHAs       (independent)
PR-3  Build provenance attestation         (depends: PR-2)
PR-4  Bundle checksum tamper tests         (independent)
PR-5  Shipped verifier symlink coverage    (depends: PR-4)
PR-6  Boundary-guard hardening             (independent)
PR-7  Confinement + TOCTOU invariant tests (independent)
PR-8  Install transaction + rollback       (depends: PR-4)

PR-10 Security invariants document         (depends: all)
```

PR-1, PR-2, PR-4, PR-6, and PR-7 are mutually independent and may land in any
order or in parallel.

## PR-1 — Make the read-only MCP surface machine-verifiable

**Objective.** Every one of the 12 tools declares `readOnlyHint: true`, and the
check fails when any tool omits it. Closes F-01.

**Files.** `mcp-server/src/server.ts`; `tools/check-mcp-server.mjs`;
`mcp-server/test/server.test.ts`; `mcp-server/test/application-boundary.test.ts`

**Changes.**

- Add `annotations: { readOnlyHint: true, destructiveHint: false, idempotentHint: true, openWorldHint }` to the ten registrations that lack it. `openWorldHint: true` for the four `github_project_*` tools and `github_provider_diagnostics` (they reach the network on call); `false` for the four local `project_*` document tools and `provider_status`.
- Invert the check at `tools/check-mcp-server.mjs:168-178` to require `readOnlyHint === true` and `destructiveHint === false` on **every** tool; an absent or missing annotation fails. Remove the comment that licences absence.
- Assert `openWorldHint` matches a declared per-tool expectation, so a local tool cannot silently acquire network reach.

**Tests.** Positive: all 12 tools expose `readOnlyHint: true`. Negative: a
fixture registration omitting `annotations` fails the inverted check; one
declaring `readOnlyHint: false` fails; one declaring `destructiveHint: true`
fails. Assert the 12-name set and fixed registration order are unchanged.

**Acceptance.** `pnpm mcp:smoke` passes and fails for the right reason when an
annotation is removed. Tool count, names, order, and schemas byte-unchanged. No
`docs/security-model.md` claim becomes false.

**Rollback.** Revert; annotations are advisory metadata, so no behaviour depends
on them.

**Risk.** Low. Additive metadata plus a stricter check.

## PR-2 — Pin every GitHub Action to a commit SHA

**Objective.** No workflow resolves a mutable ref. Closes F-03.

**Files.** all 12 files in `.github/workflows/`; optionally
`.github/dependabot.yml`

**Changes.**

- Replace every `uses: owner/repo@vN` with `uses: owner/repo@<40-char-sha>  # vN`.
- Replace `dtolnay/rust-toolchain@stable` — a branch ref in the artifact-producing job — with a pinned SHA.
- Reconcile `actions/upload-artifact` / `actions/download-artifact` to one version across all workflows.
- Add a CI step (or `actionlint`/`zizmor`) that fails on any `uses:` not matching `@[0-9a-f]{40}`.
- If Dependabot `github-actions` updates are not already enabled, add them so pins are maintained rather than frozen.

**Tests.** A repository-validation check greps every workflow for unpinned
`uses:` and fails; a negative fixture with a tag ref is rejected.

**Acceptance.** Zero unpinned `uses:` repo-wide. CI green. Each pinned SHA
verified to be the commit the intended tag points to. Release workflows are not
executed by this PR; the diff is inspected for equivalence.

**Rollback.** Revert. Pins are inert metadata; reverting restores prior
resolution.

**Risk.** Low-Medium. A wrong SHA breaks CI immediately and visibly, which is
the failure mode you want.

## PR-3 — Publish build provenance for release assets

**Objective.** A published release carries a verifiable attestation over all
three assets, so a substituted artifact is detectable and attributable. Closes
F-02.

**Files.** `.github/workflows/release-v0.6.yml`; `SECURITY.md`;
`docs/releases/README.md` (verification instructions)

**Depends on.** PR-2 — attesting with unpinned actions in the build job would
certify an artifact produced by mutable third-party code.

**Changes.**

- Add `actions/attest-build-provenance` (SHA-pinned) to the publish job, covering the tar.gz, the zip, and the external `SHA256SUMS.txt`.
- Add `id-token: write` **to that job only**, alongside its existing `contents: write`. No other workflow or job gains the permission.
- Document `gh attestation verify <asset> --repo he8um/oh-my-pm` in `SECURITY.md` as the user-facing check, and state plainly what it does and does not prove.
- Leave the `installer/` placeholder signature untouched and still unwired; do not conflate the two.

**Tests.** Not unit-testable — verified operationally at the next release.
Add a repository check asserting `id-token: write` appears in exactly one job
across all workflows, so the permission cannot spread unnoticed.

**Acceptance.** The publish job emits an attestation for all three assets;
`gh attestation verify` succeeds on genuine assets and fails on a locally
modified copy; `id-token` is confined to the publish job; the release remains
gated by the existing branch, version, confirmation, lineage, and environment
gates.

**Rollback.** Revert. Attestation is additive — checksum verification is
unaffected, and the installer's four verification passes are untouched.

**Risk.** Medium. It edits the release workflow, which is the highest-consequence
file in the repository. Mitigated by touching only the publish job and adding no
new gate. **This PR must not be merged as part of an actual release run.**

## PR-5 — Cover symlinks in the shipped bundle verifier

**Objective.** The verifier shipped inside every bundle accounts for symlinks
instead of skipping them. Closes F-04.

**Files.** `tools/check-release-bundle.mjs`; `tools/release-bundle-utils.mjs`;
`distribution/libexec/release-install-core.test.mjs`

**Depends on.** PR-4 — the checksum tamper tests establish the fixture
scaffolding this PR extends.

**Changes.**

- Replace the unconditional `if (entry.isSymbolicLink()) continue;` at `check-release-bundle.mjs:86` with enumeration that records symlinks and asserts each resolves inside the bundle root, mirroring `release-bundle-utils.mjs:750-751`.
- Decide and document one rule for symlink coverage in `SHA256SUMS`: either cover link targets, or keep them excluded **and** add an explicit escape check so exclusion is a stated policy rather than an accident.
- Keep the reason vocabulary aligned with the installer's existing `bundle_symlink_escape` / `bundle_dangling_symlink` codes.

**Tests.** Fixture bundles containing an escaping symlink, a dangling symlink,
and a benign inside-root symlink: the first two are rejected by the shipped
verifier; the third is accounted for rather than invisible. Assert the installer
and the shipped verifier now agree on all three.

**Acceptance.** The shipped verifier independently rejects escaping and dangling
symlinks. Existing bundles that contain no symlinks verify byte-identically, so
no released artifact's verification result changes.

**Rollback.** Revert. Note the verifier is _shipped inside bundles_, so a change
here affects future bundles only — already-published bundles carry their own
copy and are unaffected.

**Risk.** Low-Medium. Touches release verification; mitigated by requiring
byte-identical results on symlink-free bundles.

## PR-6 — Turn boundary discipline into boundary enforcement

**Objective.** Extend existing static guards to the places currently protected by
convention. Closes the enforceable parts of F-09.

**Files.** `tools/validate-boundaries.mjs`; `mcp-server/test/*`;
`application/src/node/github-token.ts`; `providers/src/github/provider.ts`

**Changes.**

- **Extend the stdout ban to `mcp-server/src/**`.** The rule at `:716-744` covers only the three bin wrappers, yet stdout cleanliness is the invariant whose breach corrupts the protocol stream. Ban `console.*` and `process.stdout` in `mcp-server/src/**` (no violation exists today, so this is codification).
- **Assert allowlists are non-stale.** Fail when an entry in `GITHUB_TOKEN_ENV_ALLOWED`, `GITHUB_PRODUCTION_FILES`, or `OH_MY_PM_PROVIDER_CONFIG`'s allowlist names a path that does not exist — `cli/src/github-token.ts` at `:1220` is currently such an entry.
- **Add a token charset assertion** in `readGitHubTokenFromEnvironment`: reject a value containing CR, LF, or any control character, so header-injection rejection is local rather than delegated to Node's HTTP stack. Keep it a charset check, not a format allowlist — GitHub token formats change, and rejecting a valid future token would be worse than the risk.
- **Assert the search-scope invariant at its use site.** `runIssueSearch` is the only place scope and terms combine; add an assertion there that terms contain no forbidden qualifier, so the guarantee no longer lives in exactly one upstream call path (`providers/src/github/query.ts:280-296`).
- **Cap directory-walk depth** in `collectCandidates` (`application/src/node/project-documents.ts`), matching the depth cap the privacy scanners already use, with a warning code consistent with the existing document-limit warnings.

**Tests.** Negative fixtures for each new rule: a `console.log` in
`mcp-server/src/`, a stale allowlist entry, a CRLF-bearing token, a
qualifier-bearing term reaching `runIssueSearch` directly, and a
deeper-than-cap directory tree. Assert the depth warning is emitted rather than a
crash, and that no existing document fixture changes result.

**Acceptance.** `pnpm validate` fails for each new violation and passes on a
clean tree. No behavioural change for any valid input — verified by the existing
suites passing unchanged.

**Rollback.** Revert per-guard; each is independent.

**Risk.** Low. Mostly static analysis. The token charset check is the only
runtime path, and it fails closed on input that the HTTP stack already rejects.

## PR-7 — Make confinement and TOCTOU resistance measurable

**Objective.** Convert the confinement guarantees into named, asserted
invariants — without overclaiming the documented residual.

**Files.** `project-memory/test/path-safety.test.ts`;
`project-memory/test/physical-confinement.test.ts`;
`application/test/project-documents.test.ts`

**Changes.**

- Add a test that names each invariant from the invariants table below and asserts it directly, so a future reader can map invariant → test.
- Add the hop-chain case explicitly: a route that leaves the root and returns (`<root>/hop → <outside>/back → <root>/real`) is rejected, which is the case a single `realpath` would accept. The implementation already handles this (`physical-confinement.ts:20-25`); the assertion pins it.
- Add the "validated immediately before the write" assertion, and a comment stating what is **not** claimed (atomic race-freedom), matching `physical-confinement.ts:33-41`.
- Assert the privacy key-scan runs on every persistence path — either by a chokepoint that makes omission unrepresentable, or by a test that exercises each write path with a planted forbidden key. Prefer the chokepoint; it is the only remaining place where a new code path could bypass a control.

**Tests.** As above, plus a negative test per invariant.

**Acceptance.** Every invariant in the table below maps to at least one test by
name. No production behaviour changes. The documented TOCTOU residual remains
documented and is not restated as a guarantee.

**Rollback.** Revert; tests only, unless the privacy chokepoint is implemented,
in which case that commit is separable.

**Risk.** Low. Test-first, with one optional structural change.

## PR-8 — Harden the install transaction and rollback

**Objective.** Unpredictable transaction directories; rollback that preserves
evidence and reports its own failure. Closes F-06 and F-08.

**Files.** `distribution/libexec/release-install-core.mjs`;
`tools/release-archive-utils.mjs`; `tools/release-bundle-utils.mjs`;
`distribution/libexec/release-install-core.test.mjs`

**Depends on.** PR-4 — fault-injection tests build on that scaffolding.

**Changes.**

- Replace PID-derived temp paths with `mkdtempSync`, matching `tools/check-release-archives.mjs:221-222`. Removes the recursive `rmSync` of a predictable path.
- Preserve backups until **after** a verified successful restore; move `cleanupTempOnly()` so a failed rename-back cannot be followed by deletion of the backup.
- Add a distinct reason code for "rollback itself failed", so a mixed-state prefix is reported rather than silently swallowed by the `try {} catch {}` chain.
- Replace the Windows `shell: true` in `release-bundle-utils.mjs:224` with a direct executable invocation, and stop ignoring the deploy exit code (`:972-974`) or state in a comment why the structural checks are sufficient.

**Tests.** Fault injection that forces post-install verification failure and
asserts: the prefix returns to its exact prior state; backups survive a failed
restore; the new reason code appears; no predictable temp path is created. Assert
no spawn uses `shell: true`, extending the existing source-level assertions at
`tools/check-release-install.test.mjs:176,179`.

**Acceptance.** Rollback is exercised by test for the first time. Idempotent
install, drift blocking, and `--force` semantics are unchanged.

**Rollback.** Revert. Higher care than most PRs here: this code runs on user
machines during install.

**Risk.** Medium. It edits the install transaction. Mitigated by additive
changes only and by proving unchanged behaviour on the happy paths already
covered by 34 + 16 existing tests.

violated. Rows marked **new** are established by this plan; the rest already hold
and are being made explicit.
